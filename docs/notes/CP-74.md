**What the code already has (read, not built):**
- Lessons are `session` rows (`subject_code`, `kind`, `text`, `activity_code`, `plan_entry_id`); no objective column yet.
- `engine/w2_print/tt_heads.py`: `offers(conn, session_id, who=)` is the K2 *activity* offer (by the lesson's head); `ensure_offered`, `heads_in`,
  `groups_of`. Routes `/timetable/lesson/offers` and `/timetable/lesson/edit` are in `api/routes/timetable_hand.py` (line ~163-182), written through
  `tt_edit`. The new picker extends these (design F3), it does not replace the K2 path: K2 stays activity-first.
- `learning_objective` (`supabase/migrations/20260921090000_full_registry.sql`): `code` (LO-G2-0480), `band`, `subject` (the school's spelling, e.g.
  "Numeracy"), `unit`, `title`, `signal`; later migrations added more (check `\d learning_objective`: `retired`, `kind` are named in the design).
  `activity_objective` links activities to objectives (2,669 links live on 17 Nov). A head resolves to a subject through `tt_heads.heads_in` and the
  school's spellings (`core/subject_map`), so join objectives to lessons on that one answer (spec S1 of CP-71).
- Design D4: `rank(objectives, pointer, taught, links) -> tiers` is one pure function; tiers Next up / Rest of the unit / Next unit / All of the subject;
  ties break: not yet taught this year, then has an activity for this grade, then `ord`. D3: the pointer is the objective of the most recent past lesson
  that has one and is not `not_done` or `moved`; a past lesson still `planned` counts "not confirmed". D5: `spread` arithmetic, same-as-last-week,
  continue (suggestion job; machine-made, only where there is an order and a pointer).
- Solver: FET lives in `engine/adapters/fet.py` (one class, no educators); `w2_print/tt_generate.py`, `tt_need.py` (arithmetic checks), `tt_live*.py`
  (go-live). `tt_check.py` is the pure checker every solver answer must pass; `tt_check_fix.py` shows the pattern of running a candidate back through it.
  Pattern cells carry `source` (`machine`/`person`): the solver pins every `person` cell. `timetable_run` is append-only, one row per run, kept even when
  unused. `timetable.solve_seconds` (120) and `timetable.seed` are existing setting rows. Estimate in the design: well under 5 s; not measured.
- Phase 1's Build page is `apps/web/app/(app)/timetable/build/` (`paint.tsx` holds one Undo history of cell and rule steps; a solver result becomes one
  `cells` step whose inverse the engine returns). The panel, `read-panel.tsx` (phone), `lib/timetable-check.ts`, `lib/timetable-rules.ts` are there.

**Lessons from Phase 1 (each cost a CI run):**
- `bin/check` does **not** run the core. Run `packages/engine/tests/core.txt` on a clean database before pushing (`grep -v '^#' tests/core.txt | grep -v '^$'
  | xargs uv run pytest`), and `playwright test --list --grep @core` must stay at 120. The engine core is 230.
- A test added to a file that `core.txt` names as a whole file (e.g. `test_tt_pattern_routes.py`, `test_tt_pattern.py`) raises the core. Put new tests in
  files of their own.
- Every exported server action in `app/**/actions.ts` must call `requireStaff()` in its own body (`test_web_gate`).
- Local browser runs regenerate committed screenshots (`docs/notes/img`, and other specs' `docs/screens/**`): commit only your own `cp74-*`.
- A local database that browser specs have written to makes engine tests that look at "every class with a pattern" fail. Use a clean one
  (`bin/testdb fresh postgresql://postgres:pw@localhost:5432/<name>`, about 10 minutes, wait until it finishes) for the core.
- Specs need classes of their own in a year of their own (new each run); the `u110` to `u112` specs show how.
- `test_web_identity` fails in this container (Node cannot resolve an extension-less import); it is environmental.
