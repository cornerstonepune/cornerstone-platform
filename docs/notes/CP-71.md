## State (the rules door, 17 Nov 2026; branch `cp-71-rules-door`, off main)

- **Why.** The Build page's rules panel (design E) needs to write "most in a day", Must / Try to, and an educator's days away. The old door
  (`tt_rules._limit`) refused a day's span, took no strength, had no `away`, and refused a count for a subject not yet placed (so "counts
  before cells", design A3, could not work). No schema change: the columns are migration `20270202090000`'s.
- **`w2_print/tt_rules_door.py`** is now the one door behind `/timetable/rules/read` and `/change` (the Timetable rules page and the panel).
  It owns `limit` (day, week, fortnight; `level` must or try) and `away` (an educator of the class, a weekday, week A, B or both, a period or
  all day, a reason); period, block and fixed stay in `tt_rules` and are passed through. `read` adds `limits` (with `level`), `teaches` (the
  class educator and each subject's educator, by staff id, never a name), `away`, `heads` and `any_subject`.
- **Mapping (design E1, E2).** Must = `weight` empty; Try to = `weight` from the new setting row `timetable.weights` (by span; seed
  `config.json`), never typed by the coordinator. Unsaid, a day's limit is a Try to and a week's or fortnight's a Must; an edit that does not
  say keeps what the rule was.
- **Decision: one row for "at most 2 of one subject in a day".** A day's limit whose `subject_code` is `*` (`tt_check.ANY`) is about every
  subject; the checker expands it over the subjects the class has. The alternative (a row per subject, written thirteen at a time) drifts
  the day a new subject is painted, and makes the coordinator's one sentence thirteen rows to edit. Refused for a week or a fortnight (a
  count names its subject).
- **Who may write.** Every write on the door (`limit`, `away`, and also `period`, `block`, `fixed`) asks the coordinators' group (spec S3), as
  the pattern's writes do. **This narrows who can edit live rules:** before CP-71 anyone on the staff list could change a period, a block or a
  fixed slot (the page was only in the coordinator's menu). Decided by the orchestrator, 17 Nov.
- **The generator** (`tt_need`, FET) still reads only a week's and a fortnight's counts (`tt_rules._limits`), and treats a Try to count as
  firm. Nothing live uses it; Phase 2's solver reads the strength.
- Tests: `tests/test_tt_rules_door.py` (five, nightly: the core is at its ceiling). `test_tt_rules.py`'s person is now a coordinator.

## Decisions (session 2)

- **Who teaches.** The class's open `subject_educator` grant for the subject (a head resolves to a subject through the school's spellings, as
  `tt_heads.heads_in` does). A *subject* lesson with none falls back to the class's class teacher; a *specialist* lesson does not (a visiting
  specialist is not the class teacher). Two educators for one class and subject are not guessed between. A lesson with no named educator is
  skipped by the educator and absence checks and listed in `notes` (design F8: never a silent pass).
- **Fixes are single moves.** A fix moves one lesson of the problem to an empty place of its class (nearest first), or, when no move works, takes it
  out. A problem that needs two moves has no fix offered rather than an unproven one.
- **Allowing** a Must problem is an approval row of kind `timetable_clash` (target = `allow_key`, prefix `pat:`), by the `timetable.accept_clash_group`.
- **Not in Phase 1's checker (named, not hidden):** "fewest" of a limit (the spec names only over), an `away` rule on a date (`on_date`; the pattern
  has no dates), `after`/`share`/`run` rules (left out of the schema on purpose, S2).

## Decisions

- **Head for Grades 1 to 4 = the subject table's code**, as `timetable.heads` rows (groups are the school's spellings of that code).
  `tt_heads.heads_in` already resolves a head to its subject, so no code changed. K2 keeps `math`, `story`...
- **Left out of design section F on purpose:** `timetable_rule.other_subject_code`, kinds `after`/`share`, span `run` (not in Phase 1's scope;
  a later migration adds them if a phase needs them) and the `timetable_clash` view change (the educator clash is `tt_check`, code over the
  pattern; no reader needs the view). Pushed back on the design here: fewer columns now, nothing speculative.
- **Period key.** `period` was unique on `(tenant, grade, starts_at)`, which allows one row per start time and so one day shape. It is now
  `(tenant, grade, starts_at, valid_from)` nulls not distinct. Four test inserts (`on conflict (...)`) were updated to name the new key.
- `engine live rules` reads the *live* database by default: use `--url <local>` when regenerating `rules.json`.

- **Pattern semantics.** A change dated `F` ends the cell open on `F` the day before (or deletes it if it began on or after `F`), opens
  the new cell from `F` and gives it the old one's last day, so a later dated change survives. An edit that puts back what the day before
  said extends that earlier row instead of adding a twin, so an applied inverse restores the same rows. `clear` leaves no row; a place
  with no row reads `empty`.
- **Fixed cells.** `change` refuses to paint over or clear a `fixed` cell (it asks you to use the day's rules); fill and copy skip such
  cells and list them in `skipped`; copy never uses a fixed cell as its source; only `start_from` creates fixed cells.
- **Machine / person.** start-from and copy write `source = machine`; paint, fill and `change` write `person` (a person's cell is
  pinned for the later solver).
- **Default date.** Routes use `from_date`, else the start of the class's first teaching fortnight (not over) that has no lessons for it.
- **Group.** Every write asks `tt_live.in_group` with `timetable.go_live_group` (coordinators); reads need only a staff sign-in.
- **Not built, on purpose:** `start_from` copies periods and fixed rows only (not the subject counts the design mentions: no counts
  exist in Phase 1 yet); a class whose grade already has a day is refused (no merging of day shapes).
