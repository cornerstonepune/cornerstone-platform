# CP-12: the timetable by hand

Branch `cp-12-build` from main (fd777c84). Scope `specs/CP-12` (PR #485), design `specs/CP-12/design.md`.

## What was built
- Migration `20270125180000_a_lesson_moved_by_hand_is_kept.sql`: `timetable_move` and `timetable_clash_accept` (both
  append-only), the view `timetable_clash`, the function `timetable_fortnight_layer(class, fortnight)`, and two settings
  per school (`timetable.open_clash_blocks_approval` on, `timetable.accept_clash_group` everything). Both tables are in
  `access_table`; the move table is class data (reach of `enrolment`), the acceptance is school-wide.
- `w2_print/tt_move.py`: a move swaps what two dated cells hold; their lessons follow. Two lessons that swap are
  deleted and re-inserted at the same ids in one transaction, as CP-22's `tt_live._write` does: the session key is
  immediate, so an in-place update cannot work (the design's "update in place" does not hold). Ids, plan lines,
  `created_at` and materials links are kept. The whole move, including CP-6's frozen-change record
  (`ensure_editable`), runs in one savepoint, so a refusal writes nothing; the CLI and the route also roll back.
- Materials: CP-22's own check (`tt_live_plan._materials`) refuses a move whose list was already sent or does not
  cover the new date. A line only the moving lesson feeds follows it; a line shared with another lesson keeps its date
  (the link's own date follows). This differs from `tt_live`, which sets the line's date either way.
- `w2_print/tt_clash.py`: the clash list, the open count by kind, and `accept`.
- Commands: `engine timetable move | accept | clashes` (`cli_tt_hand.py`), `engine fortnight approve` (`cli_fortnight.py`).
- Keyed routes `POST /timetable/move` and `POST /timetable/clash/accept`, one test each; `engine-routes.ts` regenerated.
- Tests: `test_tt_move.py`, `test_tt_clash.py`, `api/test_timetable_hand_routes.py`, world in `tests/tt_hand_world.py`.

## Decisions
- The dated layer: CP-22 built it in Python, with no database function, so `timetable_fortnight_layer` is new here
  (a copy of the frame onto the fortnight's teaching dates, once, no rows if a layer exists).
- A clash key is an md5 of kind, fortnight, the sorted cells, the rule and its numbers and the count; a blocked clash
  also carries the lesson in the cell (subject and session id), so a different lesson swapped into an accepted cell is a
  different clash. An acceptance also lapses when any lesson of the clash is moved after it was accepted (checked
  against `timetable_move` in the view), so a lesson that leaves and comes back reopens it.
- Accepting needs a current grant in the group named by `timetable.accept_clash_group` (Nimish 8 Nov), checked with the
  school's day by CP-22's `tt_live.in_group`, which now takes the setting's key (go-live's default is unchanged), and
  under the same per-class advisory lock a move takes.
- Routes: design decision 8 said "no API route", but docs/backend-plan.md rule 6 (CP-24) says a Core scope a screen
  will call ships one keyed route beside its command, so `POST /timetable/move` and `/timetable/clash/accept` stay.
